# Landing Page 設計文件

## Context

這是 Pocketit 專案的第一個使用者面向頁面,需要建立強烈的第一印象並清楚傳達產品價值。Landing Page 將作為產品的門面,吸引潛在使用者了解並開始使用 Pocketit。

目前專案僅有 Vite + React 預設模板,需要完全替換為自訂的 Landing Page。

## Goals / Non-Goals

### Goals

- 建立視覺吸引力強的 Landing Page,展現現代化設計美學
- 清楚傳達 Pocketit 的核心價值:統一管理各種生活記錄
- 提供響應式設計,支援桌面和行動裝置
- 實作深色/淺色模式,提升使用者體驗
- 遵循 SEO 最佳實踐,確保搜尋引擎友善

### Non-Goals

- 不實作使用者註冊/登入功能(後續階段)
- 不建立實際的記錄管理功能(後續階段)
- 不整合後端 API(目前為純前端展示)
- 不使用 UI 框架(如 Material-UI、Ant Design),保持輕量化

## Decisions

### 技術決策

#### 1. 元件架構

**決策**: 採用單檔案元件結構,將 Landing Page 主要內容放在 `App.tsx` 中,必要時才拆分子元件。

**理由**:

- Landing Page 是相對靜態的展示頁面,不需要複雜的元件層級
- 遵循「簡單優先」原則,避免過早優化
- 如果未來需要重用元件,再進行拆分

**替代方案**:

- 一開始就建立完整的元件庫 → 過度設計,增加複雜度
- 使用現成 UI 框架 → 增加依賴,不符合輕量化目標

#### 2. 樣式方案

**決策**: 使用 Vanilla CSS + CSS 變數建立設計系統。

**理由**:

- 專案已配置 Vite,原生支援 CSS
- CSS 變數提供足夠的主題化能力(深色/淺色模式)
- 不需要額外的建置配置或依賴
- 符合專案慣例(避免 TailwindCSS 除非明確要求)

**替代方案**:

- CSS-in-JS(styled-components、emotion) → 增加依賴和學習曲線
- TailwindCSS → 使用者未明確要求,且會增加建置複雜度

#### 3. 色彩系統

**決策**: 使用 HSL 色彩空間定義漸層色系,避免使用純色(紅、藍、綠)。

**理由**:

- HSL 更容易調整色調、飽和度和亮度
- 漸層色彩提供現代化、高級感的視覺效果
- 符合「視覺卓越優先」的設計原則

**色彩方案建議**:

```css
--primary-hue: 250;
--primary: hsl(var(--primary-hue), 70%, 60%);
--primary-light: hsl(var(--primary-hue), 70%, 70%);
--primary-dark: hsl(var(--primary-hue), 70%, 50%);
```

#### 4. 字體選擇

**決策**: 使用 Google Fonts 的 Inter 或 Outfit 字體。

**理由**:

- 現代化、易讀性高
- 支援多種字重,提供設計彈性
- 免費且易於整合

#### 5. 圖示/插圖

**決策**: 使用 AI 圖片生成工具(`generate_image`)建立自訂插圖。

**理由**:

- 避免使用佔位符,提供完整的展示效果
- 自訂插圖更符合品牌調性
- 不依賴外部圖示庫

### 架構決策

#### 頁面結構

```
Landing Page
├── Hero Section
│   ├── 主標題
│   ├── 副標題
│   ├── CTA 按鈕
│   └── 視覺裝飾
├── Features Section
│   └── 6 個 Feature Cards
│       ├── 願望清單
│       ├── 電影記錄
│       ├── 保養品/化妝品記錄
│       ├── 書籍記錄
│       ├── 電視劇記錄
│       └── 漫畫記錄
├── How It Works Section
│   └── 3-4 個步驟說明
└── CTA Section
    └── 底部行動呼籲
```

#### 深色/淺色模式實作

**決策**: 使用 CSS `prefers-color-scheme` 媒體查詢自動偵測系統偏好。

**理由**:

- 無需額外的 JavaScript 狀態管理
- 自動跟隨使用者系統設定
- 效能最佳,無閃爍問題

**未來擴充**: 可加入手動切換按鈕,覆寫系統偏好。

## Risks / Trade-offs

### 風險 1: 設計過於複雜

**風險**: 過度追求視覺效果,導致開發時間過長或效能問題。

**緩解措施**:

- 優先實作核心內容和結構
- 動畫和裝飾效果作為最後優化步驟
- 使用 CSS `will-change` 和 `transform` 確保動畫效能

### 風險 2: 響應式設計測試不足

**風險**: 在某些裝置或螢幕尺寸上顯示異常。

**緩解措施**:

- 使用瀏覽器開發者工具測試常見裝置尺寸
- 遵循行動優先(Mobile-First)設計原則
- 使用相對單位(rem、em、%)而非固定像素

### Trade-off: 靜態內容 vs 動態載入

**選擇**: 初期使用靜態內容,不從 API 載入。

**理由**:

- 簡化實作,專注於 UI/UX
- 後端尚未建立,無 API 可用
- 未來可輕鬆替換為動態內容

## Migration Plan

### 步驟

1. 備份現有的 `App.tsx`、`App.css`、`index.css`(可選,因為是預設模板)
2. 實作新的 Landing Page 元件和樣式
3. 在本地開發環境測試(`pnpm dev`)
4. 執行生產建置測試(`pnpm build` + `pnpm preview`)
5. 部署到生產環境

### Rollback

如果需要回滾:

- 使用 Git 恢復到變更前的 commit
- 或手動恢復備份的檔案
